# 项目整理与桌面端优先计划

## 1. 当前事实

### 1.1 初始化仓库现在做了什么

当前桌面端的“初始化仓库”已经不只是写本地配置。

它现在会：

1. 保存本地 `profiles/settings.env`
2. 生成一个“最小运行集”临时仓库
3. 把最小运行集同步到目标私有仓库分支

当前默认同步内容包括：

- `.github/workflows/upload.yml`
- `scripts/`
- `profiles/example.env`
- `.gitignore`
- 最小 README

不会同步：

- `desktop/src`
- `desktop/src-tauri`
- 开发文档
- 本地敏感文件，例如：
  - `profiles/accounts.json`
  - `profiles/settings.env`
  - `desktop/node_modules`
  - `desktop/dist`

### 1.2 真正上传到临时 Release 的文件

需要区分两层：

1. 初始化仓库时同步到私有仓库的是“模板代码”
2. 真正上传 IPA 时放进临时 Release 的只有运行材料：
   - `package.ipa`
   - `AuthKey.p8`
   - `issuer_id.txt`
   - `key_id.txt`

所以“同步模板仓库内容”和“上传到临时 Release 的文件”不是一回事。

### 1.3 当前主要问题

当前流程已经基本可用，但项目层面还有两个主要问题：

1. 仓库职责混在一起
   - CLI 脚本
   - 桌面端
   - 文档
   - workflow
   现在都在根目录附近，后续维护会越来越乱

2. 入口还不够统一
   - 现在 CLI 和桌面端都能跑
   - 但目标已经很明确：后续优先桌面端，CLI 降为兼容和调试工具

## 2. 整理目标

整理的目标不是大改架构，而是把现有能力收口成一个清晰的产品形态。

目标如下：

1. 本项目后续以桌面端为主入口
2. CLI 脚本保留，但定位为底层执行器
3. 私有仓库初始化逻辑继续稳定可用
4. 后续可以自然过渡到 `.dmg` / `.exe`
5. 再往后如果要做网页，也有清晰边界，不会推倒重来

## 3. 建议的目录整理

建议整理成下面的结构：

```text
.
├── .github/
│   └── workflows/
│       └── upload.yml
├── desktop/
│   ├── src/
│   ├── src-tauri/
│   └── package.json
├── scripts/
│   ├── bootstrap.sh
│   ├── bootstrap.ps1
│   ├── deploy.sh
│   └── deploy.ps1
├── profiles/
│   ├── .gitkeep
│   └── example.env
├── docs/
│   ├── project-reorg-plan.md
│   ├── desktop-dev.md
│   └── user-guide.md
├── README.md
└── LICENSE
```

整理原则：

1. 根目录只保留入口级文件
2. 所有脚本收进 `scripts/`
3. 桌面端独立在 `desktop/`
4. 文档统一放 `docs/`
5. `profiles/` 继续保留在仓库根目录，避免和现有脚本状态格式脱节

## 4. 私有仓库同步内容优化方案

### 4.1 当前方案

当前已经切换到：

- 初始化时同步最小运行集

优点：

- 用户私有仓库更干净
- 保留 workflow 和脚本的运行闭环
- 仍然方便排查上传问题

### 4.2 当前同步清单

当前同步这些内容到用户私有仓库：

- `.github/workflows/upload.yml`
- `scripts/`
- `profiles/example.env`
- 必要的 README 或最小使用说明

不再默认同步：

- `desktop/src`
- `desktop/src-tauri`
- 开发文档
- 构建配置

### 4.3 当前实现方式

当前实现不是直接把本地仓库 `HEAD` 推过去，而是：

1. 在本地生成临时同步仓库
2. 拉取目标私有仓库分支历史（如果存在）
3. 清空工作树并写入最小运行集
4. 生成同步提交并推送到目标分支

这样做的好处是：

- 私有仓库内容保持最小化
- 已有分支历史可以继续衔接
- 桌面端和公开模板仓库的开发文件不会被默认带过去

## 5. 后续阶段计划

### Phase 1：结构整理

目标：

- 把脚本移到 `scripts/`
- 补文档拆分
- 更新桌面端和脚本里的路径引用
- 保持当前上传流程不变

完成标准：

- 桌面端还能跑
- CLI 还能跑
- README 更清晰

### Phase 2：桌面端主入口化

目标：

- README 以桌面端为主说明
- CLI 降为高级用法 / 兼容方案
- 初始化仓库、测试连接、上传都优先通过 GUI 完成

完成标准：

- 普通用户不再需要先学命令行

### Phase 3：精简私有仓库同步内容

目标：

- 初始化仓库时，不再默认推整个模板仓库
- 改为同步最小运行集

完成标准：

- 私有仓库更干净
- 仍能正常上传
- 仍保留必要排错信息

### Phase 4：打包与产品化

目标：

- macOS 产出 `.dmg`
- Windows 产出 `.exe` / 安装包
- 增加首次启动引导

完成标准：

- 用户打开 App 后即可完成配置和上传

### Phase 5：网页方向预研

这不是当前要做的，但要提前明确边界。

如果未来做网页，推荐只把“管理界面”网页化，不把 Apple key 和上传执行统一托管到我们自己的服务端，避免多租户和账号隔离风险。

建议方向：

- 网页做说明、配置引导、状态查看
- 真正执行仍保留在用户自己的 GitHub 私有仓库 / 本地客户端

## 6. 当前建议结论

现阶段建议如下：

1. 仓库结构整理已经完成
2. 继续以桌面端作为第一入口
3. CLI 继续保留，但退到底层
4. 优先推进打包和首次启动体验
5. 初始化仓库默认同步最小运行集，避免把开发文件带入私有仓库

## 7. 下一步执行建议

建议按这个顺序继续：

1. 继续完善桌面端首次使用引导
2. 开始打包 `.dmg`
3. 开始打包 Windows 安装包
4. 增加首次启动向导
5. 再决定是否需要网页辅助层

当前状态：

- Phase 1 已完成
- Phase 2 已完成主要目标
- Phase 3 已完成

这条路线风险最低，也最符合现在“流程已经跑顺，先整理再产品化”的状态。
